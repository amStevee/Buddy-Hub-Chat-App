# Database Documentation

## Database system

- Database: PostgreSQL
- ORM: Prisma
- Runtime client: Prisma Client
- Production provider: PostgreSQL-compatible hosting (for example Neon)

## Overview

The database supports:

- user accounts and authentication
- direct chat rooms
- room membership and hidden-room state
- real-time message history

## Current schema

### users

Stores authentication and profile data.

| Column        | Type     | Constraints       | Notes                                |
| ------------- | -------- | ----------------- | ------------------------------------ |
| id            | String   | primary key, UUID | Generated by Prisma                  |
| first_name    | String   | not null          | Max 50 characters                    |
| last_name     | String   | not null          | Max 50 characters                    |
| phone         | String   | unique, not null  | Stored in normalized Nigerian format |
| email         | String   | unique, not null  | Lowercased before save               |
| password_hash | String   | not null          | Hashed password                      |
| created_at    | DateTime | default now       | Audit timestamp                      |

### rooms

Stores chat room metadata.

| Column     | Type     | Constraints  | Notes                                     |
| ---------- | -------- | ------------ | ----------------------------------------- |
| id         | String   | unique, UUID | Generated by Prisma                       |
| name       | String   | not null     | Room identifier derived from participants |
| created_at | DateTime | default now  | Room creation time                        |

### room_participant

Tracks which users belong to each room.

| Column  | Type    | Constraints   | Notes                                                   |
| ------- | ------- | ------------- | ------------------------------------------------------- |
| id      | String  | unique, UUID  | Generated by Prisma                                     |
| room_id | String  | foreign key   | References rooms.id                                     |
| user_id | String  | foreign key   | References users.id                                     |
| hidden  | Boolean | default false | Used when a user removes a conversation from their list |

### messages

Stores chat history.

| Column     | Type     | Constraints  | Notes               |
| ---------- | -------- | ------------ | ------------------- |
| id         | String   | unique, UUID | Generated by Prisma |
| text       | String   | not null     | Message body        |
| sender_id  | String   | foreign key  | References users.id |
| room_id    | String   | foreign key  | References rooms.id |
| created_at | DateTime | default now  | Message timestamp   |

## Relationships

- One user can send many messages.
- One room can contain many messages.
- One room can have many participants.
- Each participant belongs to one room and one user.

## Important behavior

- Room lists only include participants whose `hidden` flag is false.
- Account deletion removes related room, participant, and message records for the deleted user’s conversations.
- Message lookups are indexed by `room_id` and `created_at` for chat-history retrieval.

## Prisma setup

The Prisma schema lives in [server/prisma/schema.prisma](../server/prisma/schema.prisma).

To generate the client locally:

```bash
cd server
npx prisma generate
```

To apply schema changes:

```bash
cd server
npx prisma migrate dev
```

## Environment variable

Set a PostgreSQL connection string in the server environment:

```env
DATABASE_URL="postgresql://postgres:password@localhost:5432/buddy_hub_dev?schema=public"
```

Whenever schema changes are made:

## 1. Update schema.prisma

Example:

```prisma
model User {
  id       Int    @id @default(uuid())
  username String @unique
}
```

## 2. Create Migration

```bash
npx prisma migrate dev --name add_user_profile
```

## 3. Commit Generated Migration

Always commit:

```text
prisma/schema.prisma
prisma/migrations/
```

Never delete migration history after it has been shared with the team.


---

## Apply Migrations in Production

Production should **never** use:

```bash
npx prisma migrate dev
```

Use:

```bash
npx prisma migrate deploy
```

This command:

- Applies existing migrations
- Does not create new migrations
- Is safe for CI/CD deployments

# Common Queries

## Fetch Room Messages

```sql
SELECT *
FROM messages
WHERE room_id = $1
ORDER BY created_at ASC;
```

## Create Message

```sql
INSERT INTO messages(text, sender_id, room_id)
VALUES($1, $2, $3)
RETURNING *;
```

# Performance Notes

- Frequently queried columns should be indexed.
- Avoid `SELECT *` in production-heavy queries.
- Message pagination should be implemented as data grows.
- Use Prisma query selection to avoid fetching unnecessary fields.

---

# Security Notes

- Never expose `DATABASE_URL`.
- Store passwords using bcrypt hashing.
- Always validate user input before persistence.
- Use Prisma parameterized queries to prevent SQL injection.
- Restrict production database access to deployment environments only.

---

# Backup & Recovery Strategy

## Development

- Local backups are optional.
- Database can be recreated from Prisma migrations.

## Production (Neon)

Recommended:

- Enable Neon automated backups.
- Enable point-in-time recovery.
- Use separate databases for:
  - Development
  - Staging
  - Production

Recovery process:

1. Restore Neon backup.
2. Run:

```bash
npx prisma migrate deploy
```

to ensure schema consistency.
